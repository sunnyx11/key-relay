# 本地日常验证与并行发布

关联规范：[发布说明](../../../release.md)、[项目架构](../../../project/architecture.md)、[项目原则](../../../project/principles.md)

## 变更原因

日常验证在本地执行，版本标签触发发布检查与安装包构建并行执行。

## 变更前

- 标签发布在单个 Windows 任务中依次执行前端检查、Rust 检查、规范检查、浏览器测试和安装包构建。
- npm 下载使用缓存，Rust 依赖和编译产物每次重新准备。
- 仓库没有默认分支 CI，标签之间无法互相读取 GitHub Actions 缓存。
- 浏览器测试安装完整 Chromium 和 Chromium Headless Shell。

此前实现的默认分支 CI 在 `main` 推送时执行检查和 Release 编译，并为标签任务准备缓存。标签发布已采用并行检查和构建。

## 变更后

- 日常开发在本地按影响范围执行检查和测试，并生成 Windows 免安装程序供人工测试。GitHub Actions 在推送版本标签时执行发布流程。
- 前端检查包含代码检查、组件测试、发布脚本测试、规范索引一致性检查及浏览器测试。浏览器只安装 Chromium Headless Shell。
- Rust 检查包含格式检查、Clippy 和常规 Rust 测试。
- 发布任务使用 Windows Server 2022 x64、Node.js 22.22.2、Rust 1.91.1 和锁文件中的依赖。
- Rust 检查与 Release 编译使用独立缓存键，标签任务只恢复可用缓存。缓存缺失时执行完整检查和编译。
- 有效标签触发并行前端检查、Rust 检查和安装包构建。构建保留版本校验、签名要求、附件准备和锁文件一致性检查。
- Release 草稿等待三个任务全部成功。任一检查或构建失败时，草稿任务跳过。同标签发布保持串行，草稿权限与只读任务分开。
- 缓存命中后仍执行检查和构建。实际耗时和缓存命中由 GitHub 托管环境验证。

示例：推送有效标签 `v0.2.0` 后，三个标签任务并行执行检查或构建，全部成功后创建 Release 草稿。Rust 检查失败时，即使安装包构建成功，草稿任务仍跳过。
