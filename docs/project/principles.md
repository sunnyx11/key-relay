## 测试要求

功能验收以需求中的处理规则、数据示例和边界情况为依据。模拟输入的兼容性声明需要对应 Windows 环境和目标程序中的实际验证。

- 常规自动测试覆盖文本、设置、任务状态与界面；系统输入通过可控接收窗口进行集成验证。
- 会发送真实桌面事件的测试使用显式入口，常规测试保持当前桌面输入不变。
- RDP 实际兼容性由使用者后续人工验收，开发交付记录其待验证状态。
- 前端单元测试与源文件相邻，Rust 单元测试位于相应模块；浏览器测试位于 `tests/e2e/`，人工验收说明位于 `tests/manual/`。
- 发布脚本测试位于 `scripts/*.test.mjs`，通过 `npm run test:release` 验证版本、更新说明、附件完整性及草稿操作契约。测试使用临时文件和 GitHub 客户端替身。
- 发布配置的本地验证与 GitHub 托管环境验证分别记录。首次标签构建须检查实际任务结果、令牌权限和 Release 附件，操作说明见[版本发布](../release.md)。

界面验收对照[视觉基准](../domains/text-input/design.md#界面视觉基准)，覆盖以下场景：

- 默认桌面布局：检查页面结构、颜色、字体、控件尺寸与间距。
- 窄窗口：检查 390px、320px 视口，以及 520px、420px 视口断点两侧的布局；文字和控件完整显示。底部操作区另按工具窗口内容盒 420px 断点两侧检查，并确认 510px 宽窗口的状态与按钮保持同行。
- 缩放：在 100% 和 150% 下检查可读性、控件完整性及页签等高。浏览器 CSS 缩放用于原型检查，桌面应用还需验证 Windows 系统缩放。
- 视口高度：检查默认 600×340、最小 320×340、普通 600×450 及同宽 881px 高的窗口。四个页签的外框填满当前可视区域，顶部与底部保留自身高度，中间区域随窗口增高或缩短。编辑框由窗口分配高度，文本在内部滚动；历史列表、历史全文、设置、关于和许可证使用各自区域的内部滚动。最大化和还原后仍满足这些规则。
- 动态状态：检查空闲、目标激活、输入进度、完成、中止及错误提示。各状态的字体、字号、字重、行高、位置和布局与空闲提示一致，仅文本与整段文字颜色变化。目标激活提示在状态区展示，取消按钮固定为 72px，操作区位置保持一致。
- 公共按钮：核对输入、历史、设置、关于、许可证及更新操作的默认、悬停、按下、焦点和禁用状态。按钮采用 26px 最小高度、13px 字号和 20px 行高，按钮组间距为 4px。检查清空的红色悬停反馈，并回归下拉框、只读编辑框和标题栏配色。
- 文本操作：在真实 Chromium／WebView2 中检查行尾空白清理、清空、逐行撤销重做、无匹配历史保留、失败后的部分编辑与草稿同步。覆盖缩进、行内空格、空行、末行、纯空白、Unicode 及清理后两种启动方式。
- 草稿与历史：临时目录验证真实读写、100 条上限、相邻去重、删除撤销、保存选项、失败重试和文件独占；浏览器验证全文查看、独立恢复、整体撤销重做、搜索与滚动位置保留、操作按钮右边缘一致及内部滚动。真实 WebView2 跨进程恢复、退出保存和升级恢复分别验证。
- 用户数据目录与单实例：验证用户主目录 `.key-relay`、文件缺失默认值、原应用配置目录文件保留，以及测试目录覆盖；真实桌面验证重复进程退出、窗口还原聚焦及编辑、页签、置顶状态保留。
- 桌面测试：通过 `KEY_RELAY_TEST_CONFIG_DIR` 指定临时配置目录，使用当前源码构建的 EXE，保留日常使用的草稿和历史。运行中应用需要隔离时，以独立应用标识构建测试程序，并通过 `KEY_RELAY_TEST_EXECUTABLE` 选择产物。
- 操作保护：检查空文本、初始化、命令提交、活动任务、安装准备和中止鼠标释放保护状态。输入中点击清理或清空仅中止任务，随后独立操作执行编辑。
- 底部居中：横向布局下，单行和多行提示的整体垂直中心与按钮组一致，分别检查 100% 和 150% 缩放。窄窗口保持状态在上、按钮在下的排列。
- 键盘操作：焦点清晰可见，隐藏内容及禁用控件退出 Tab 焦点顺序。目标详情支持悬停、键盘聚焦与 Esc 收起；长标题及负坐标在窄窗口和缩放下完整显示，主窗口高度保持一致。
- 错误提示：字段错误在设置面板内部滚动查看。存储提示占用顶部空间，任务状态在固定两行高度内换行和滚动。错误及操作反馈保持窗口尺寸，底部操作区保持可见。

## 文档维护要求

- Spec 根目录为 `docs/`，采用仓库内 [spec-coding Skill](../../.agents/skills/spec-coding/SKILL.md)。
- 首版需求建立期间，Project / Domain 按主题维护目标规范及当前事实，正文分别说明已确认要求、待确认建议和实现验证状态。
- 需求确认表示开发依据成立；已实现或已验证的声明需要对应证据。HTML 原型的验证范围与 Windows 桌面应用分别说明。
- 首版目标在 `requirements.md` 和 `design.md` 等主题文档中维护，待确认事项集中列于需求文档开头。
- 首版基准形成后的需求变化使用 Change：`proposed` 表示待确认，`accepted` 表示已确认且待完成，`completed` 表示实现验证和关联规范同步完成。
- Change 完成前，当前规范保留已生效规则，目标差异保存在该 Change 中。实现验证后同步关联规范，再标记为 `completed`。
- 本项目的首版约定优先于 Skill 中的通用生命周期规则，目录、模板、需求编号和索引检查仍按 Skill 执行。
- Change 保存需求差异；实施清单和验证输出保留在开发过程。
- 源文档更新后，依次运行索引生成和检查命令，两条命令均指定 `--specs-dir docs`。
- 三份索引由 Skill 脚本生成，维护入口见根目录 [AGENTS.md](../../AGENTS.md)。
