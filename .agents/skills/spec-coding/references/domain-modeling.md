# Domain 建模指引

## 领域划分

Domain 采用领域建模方法，依据业务能力、核心概念和规则边界组织。

1. 具有相对独立的业务目标和能力。
2. 核心概念在边界内具有一致含义，术语定义清楚。
3. 规则、数据和状态变化关联紧密。
4. 对外协作关系与职责边界明确。

领域可以是业务领域，也可以是具有独立语义和规则的平台领域。前端、数据库和工具函数等技术分类属于实现组织方式。一个需求可以对应模块或系统的一部分，归属由领域职责决定。

## 领域模型

结合实际问题描述核心对象及关系、对象身份、生命周期、状态变化、始终成立的业务约束，以及必要的一致性边界。实体、值对象、聚合和领域事件依据实际问题使用，并对应明确的业务语义。

领域间说明数据交换、调用约束和依赖方向。相同术语在不同上下文具有不同含义时，在术语表标注所属领域。

## 文档归属

| 文档 | 内容 |
| --- | --- |
| Domain `overview.md` | 目标、职责边界、核心概念和领域间关系 |
| Domain `requirements.md` | 功能用途、规则、输入输出、完整数据过程和边界结果 |
| Domain `design.md` | 当前领域模型、实现结构、接口、数据模型和技术决策 |
| Project `architecture.md` | 系统组成、跨域关系、整体数据流、集成与部署 |
| Project `glossary.md` | 术语定义及所属领域 |

必备目录、文件和模板规则见 [spec-structure.md](spec-structure.md)。当前任务涉及的内容需根据事实补充，涉及业务语义的未知项先澄清。

需求表达可观察结果；具体实现结构由设计和源码说明。相同规则保留一份完整定义，其他文档以 REQ ID 或文件链接引用。

## 同步规则

确认目标时，依据每项变化确定待更新规范，并写入 Change 的 `关联规范`：

- 领域职责或关系变化：关联 `overview.md`，必要时关联项目架构。
- 功能、约束、状态或计算规则变化：关联 `requirements.md` 及相关需求。
- 领域模型、接口或技术决策变化：关联 `design.md`。
- 项目目标、长期约束、整体架构或术语变化：关联对应 Project 文档。

Project / Domain 文档表达当前有效状态，实际验证通过后按最新确认范围同步。范围调整和完成步骤见 [usage.md](usage.md#change-开发)，跨域归属及引用规则见 [change-entry-format.md](change-entry-format.md#关联规范)。
