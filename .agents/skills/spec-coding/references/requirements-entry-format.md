# 需求内容与示例

## 模板与条目

需求文件使用 [domain-requirements.md](../templates/domain-requirements.md) 建立，条目结构和分节填写规则以该模板为准。每个需求对应一个可以独立理解和验证的功能。

- 编写或同步需求前，先查找对应的已有功能条目；已有功能的规则变化更新该条目，独立的新能力使用新条目。
- 同一功能的校验、去重、排序、回退和异常处理集中在该条目中，细则可用四级及更低级标题组织。
- 多个功能共用且具有独立语义的规则单独定义，各功能以 REQ ID 引用；功能划分依据业务目标和可观察结果。
- 同一规则保留一份完整定义；需求说明行为与约束，具体实现结构归入 `design.md`。

ID 使用 `<PREFIX>-REQ-NNN`，前缀为大写字母和数字且首位为字母，序号至少三位。ID 在 Spec 目录内唯一并保持稳定；失效 ID 不得分配给其他功能。条目排序、合并与引用维护见 [spec-structure.md](spec-structure.md#需求与引用)。脚本检查格式和当前唯一性，历史复用需要结合版本历史检查。

条目正文可以使用列表、公式、表格、下级标题和代码块。实施前必须确认当前任务相关正文充分。

## 描述要求

- 功能说明表达能力、用途和结果。
- 规则明确输入输出的含义、类型、单位、有效值、默认值、缺失和空值处理。
- 写清判断条件、公式、精度、优先级、影响结果的顺序，以及成功和失败的结果。
- 状态行为说明初始状态、转换条件和最终状态。调用条件、权限或运行条件影响结果时写入对应规则。
- 性能、安全、一致性和兼容约束采用可判定条件。
- 需求表达可观察行为；公共接口和影响结果的技术约束属于规范，局部函数拆分由源码决定。

## 完整示例

````markdown
## TEXT-REQ-001 规范化字符串列表

### 功能说明

接收字符串数组，返回清理和有序去重后的新数组，输入数组保持原值。

### 处理规则

1. 输入必须是 JSON 数组，每个元素必须是字符串。
2. 按输入顺序清理每个字符串的首尾空白。
3. 清理结果为空的元素不进入输出。
4. 按大小写敏感方式去重，保留每个值首次出现的位置。
5. 输入类型无效时返回 `INVALID_INPUT_TYPE`。
6. 任一元素类型无效时整个操作失败，返回 `INVALID_ITEM_TYPE` 和首个无效元素从 0 开始的索引。

成功结果格式为 `{"items": [<string>, ...]}`，失败结果包含 `error`，元素类型错误同时包含 `index`。

### 数据示例

输入：

```json
[" A ", "B", "A", "", "b"]
```

| 阶段 | 数据 |
| --- | --- |
| 清理首尾空白 | `["A", "B", "A", "", "b"]` |
| 忽略空项 | `["A", "B", "A", "b"]` |
| 有序去重 | `["A", "B", "b"]` |

输出：

```json
{"items":["A","B","b"]}
```

### 边界情况

| 输入 | 输出 |
| --- | --- |
| `[]` | `{"items":[]}` |
| `[" ", ""]` | `{"items":[]}` |
| `[" A ", "A"]` | `{"items":["A"]}` |
| `["A", "a"]` | `{"items":["A","a"]}` |
| `["A", 1]` | `{"error":"INVALID_ITEM_TYPE","index":1}` |
| `null` | `{"error":"INVALID_INPUT_TYPE"}` |
````

实际存在并发、重复调用、超时或部分失败行为时，需求提供对应的数据及状态过程。文档内容检查核算示例与规则是否一致。

## 引用

当前需求中的 REQ ID 可以跨领域引用，并必须指向已经声明的有效需求。Markdown 链接范围和引用检查规则见 [spec-structure.md](spec-structure.md)。
